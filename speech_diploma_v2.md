### ~11-12 минут | Редактируй под себя

## Слайд 1 — Титульный (30 сек)

Добрый день. Меня зовут Евгений, тема моей дипломной работы — **QuantumTrader Pro**, торговый терминал реального времени, разработанный на языке C++ с использованием фреймворка Qt и аппаратного рендеринга через OpenGL.

Терминал подключается к криптобирже Bybit по WebSocket, отображает рыночные данные в реальном времени и собирает данные для обучения модели машинного обучения, распознающей аномальную активность в стакане заявок.

---

## Слайд 2 — Актуальность (1 мин)

Почему это актуально?

Существующие браузерные торговые терминалы имеют три принципиальных ограничения.

Во-первых, **скорость обработки данных**. Биржа Bybit отправляет обновления тысячи раз в секунду. Браузерные решения на JavaScript не успевают обрабатывать такой поток без потерь и задержек.

Во-вторых, **рендеринг графики**. Когда на экране одновременно работают график свечей, стакан заявок и лента сделок — нужна аппаратная графика. CSS и Canvas с этим не справляются.

В-третьих, **расширяемость**. Профессиональные трейдеры хотят писать собственные индикаторы, не дожидаясь обновлений от разработчика.

Есть и четвёртая, более узкая проблема, из-за которой родилась аналитическая часть работы: крупные игроки на бирже маскируют своё присутствие — дробят ордера, выставляют и тут же снимают заявки (спуфинг). Человек физически не успевает заметить такой паттерн за доли секунды, а классический теханализ на графике свечей видит сигнал слишком поздно.

**Решение** — нативный десктопный терминал на C++, где скорость и расширяемость решаются на уровне архитектуры, а поверх — модуль сбора данных, размечающий поведение стакана для последующего обучения модели.

## Слайд 3 — Архитектура (1.5 мин)

Система построена в три слоя.

**Первый слой — источник данных.** Это Bybit WebSocket API. Биржа в реальном времени отправляет три типа сообщений: kline (свечи), orderbook (стакан) и publicTrade (лента сделок).

**Второй слой — бизнес-логика.** Здесь ключевые компоненты. BybitConnector управляет WebSocket-соединением. ByBitParser разбирает входящий JSON через simdjson. MarketDataManager управляет подписками и кэширует метаданные инструментов — список символов и шаг цены (tickSize), полученный с биржи. EventBus — шина событий на Qt-сигналах, связывающая все компоненты между собой без прямых зависимостей. Отдельно в этом слое — OrderBookHistoryManager, модуль, который на каждое обновление стакана считает рыночные признаки и накапливает их в скользящем окне для дальнейшего анализа.

**Третий слой — интерфейс.** ChartContainer, OrderBookContainer и TimeAndSalesContainer — каждый отображает свой тип данных. WindowManager на базе Qt ADS управляет расположением всех окон.

Главное преимущество такой архитектуры — модули не знают друг о друге. Добавить новый виджет, новую биржу или новый набор признаков можно, не трогая существующий код.

## Слайд 4 — Технологический стек (1 мин)

Теперь об инструментах.

**C++20** — основной язык. Даёт производительность нативного кода без накладных расходов интерпретатора или сборщика мусора, RAII для управления ресурсами, move-семантику и шаблоны. Явно применено правило пяти: в EventBus запрещены copy- и move-операции через `= delete`, потому что синглтон не должен копироваться.

**Qt 6** — UI-фреймворк. Сигналы и слоты идеально подходят для событийной архитектуры, Qt ADS добавляет полноценные dock-панели, как в профессиональных IDE.

**OpenGL** — аппаратный рендеринг через QOpenGLWidget. Графика исполняется на GPU, поэтому тысячи свечей рисуются без падения FPS.

**simdjson** — выбор сделан осознанно после сравнения трёх подходов: сначала парсинг на C#, затем стандартный Qt JSON, и наконец simdjson. После изучения бенчмарков и материалов по SIMD-инструкциям процессора выбор стал очевиден — результат меньше одной микросекунды на сообщение.

**CatBoost** — библиотека градиентного бустинга от Яндекса, подключена через C-обёртку `ModelCalcerWrapper`. Используется как для инференса готовой модели внутри терминала, так и как целевой потребитель данных, которые собирает модуль анализа стакана.

**WebSocket** — асинхронный push-канал от Bybit в реальном времени.

**CMake** с GLOB_RECURSE — новые файлы подхватываются при сборке автоматически.

## Слайд 5 — Реализованные модули отображения (1.5 мин)

В рамках работы реализованы три функциональных модуля визуализации.

**График свечей.** Построен на QOpenGLWidget — GPU рисует каждую свечу напрямую. История через REST API, live-обновление через WebSocket. Масштабирование колёсиком мыши, все таймфреймы Bybit.

**Стакан заявок, Order Book.** Полный снимок плюс инкрементальные delta-обновления. Три независимо перетаскиваемых колонки — Price, Size, Total, индикатор объёма в виде цветного бара. При любом сужении окна все три колонки остаются видимы.

**Лента сделок, Time and Sales.** Данные через топик publicTrade Bybit. Зелёный фон — покупка, красный — продажа. Авто-скролл, ручная прокрутка, буфер на 500 тиков.

## Слайд 6 — Аналитический модуль: детектор аномальной активности (2.5 мин)

Отдельный, наиболее исследовательский блок работы — сбор и разметка данных для модели, которая должна распознавать поведение крупных игроков в стакане, в частности спуфинг — выставление и быстрое снятие заявок без намерения их исполнить.

Модуль `OrderBookHistoryManager` на каждое обновление стакана считает набор признаков. Во-первых, многоуровневый дисбаланс объёма bid/ask — не только по лучшей цене, а агрегированно по нескольким уровням глубины, со сглаживанием скользящим средним по трём последним снимкам. Во-вторых, признаки спуфинга: если объём на уровне цены резко упал, модуль сверяет это падение с лентой реальных сделок за тот же промежуток времени через `TradeTick`. Если падение объёма совпадает с объёмом исполненных сделок — это честная торговля. Если сделок не было, а объём исчез — это признак отмены заявки, потенциальный спуфинг. Результат сверки — не бинарная метка, а доля необъяснённого падения, `fakeRatio`, от 0 до 1, чтобы модель могла учиться на градации, а не на жёстком пороге.

Собранные признаки хранятся в скользящем окне по времени — классическая FIFO-структура: новые данные добавляются в конец, всё, что вышло за пределы окна, скажем, двух недель, автоматически вытесняется и больше не участвует в обучении. Это разделяет две задачи: набор данных для обучения — отдельно, актуальность модели во времени — отдельно, через периодическое переобучение на свежем окне.

Для превращения признаков в обучающую выборку реализован `OrderBookCsvExporter`. Каждой строке признаков присваивается целевая метка — направление движения цены через заданный горизонт времени, найденное бинарным поиском по накопленной истории. Это упрощённая версия классического метода Triple Barrier, применяемого в количественном трейдинге для разметки временных рядов.

Для проверки всего пайплайна вживую реализован тестовый сборщик данных, который подписывается на реальный поток стакана и сделок с Bybit и в реальном времени пишет CSV с рассчитанными признаками — это уже проверено на живых данных BTCUSDT.

## Слайд 7 — Производительность (1 мин)

Три ключевых показателя.

Парсинг одного JSON-сообщения через simdjson — **меньше одной микросекунды**, примерно в 10 раз быстрее стандартных парсеров за счёт SIMD-инструкций.

Рендеринг интерфейса — стабильные **60 кадров в секунду**, OpenGL исполняется на GPU и не загружает основной поток.

Задержка данных от биржи через WebSocket — **менее 50 миллисекунд**.

Архитектурно этому способствуют три решения: EventBus устраняет лишние зависимости, абсолютные пиксели колонок исключают пересчёт на каждый фрейм, паттерн Container/Widget разделяет логику подписки и логику рендеринга.

## Слайд 8 — Перспективы (1 мин)

Система спроектирована с расчётом на развитие в двух направлениях.

Первое — доведение аналитического модуля до полноценной архитектуры из двух моделей: detector-модель на длинном окне в три месяца, которая оценивает вероятность присутствия крупного игрока, и entry-модель на коротком окне в две недели, принимающая решение о точке входа на основе признаков и скора detector-модели. Также в планах полноценная разметка через Triple Barrier с барьерами take-profit/stop-loss через ATR вместо простого горизонта по времени, и добавление второй площадки — ALOR — для кросс-биржевых признаков.

Второе — расширение самого терминала: Lua-скриптинг пользовательских индикаторов без перекомпиляции, алерты по цене, поддержка нескольких бирж через единый интерфейс IConnector, Watchlist с live-ценами. Архитектура EventBus уже готова к этим расширениям без изменения существующего кода.

## Возможные вопросы и ответы

**— Почему C++, а не Python или Java?**
C++ даёт прямой контроль над памятью и производительность без garbage collector. Для торгового терминала, где каждая миллисекунда важна, это принципиально — как для рендеринга, так и для обработки потока рыночных данных в реальном времени.

**— Как обеспечивается потокобезопасность при работе с WebSocket?**
WebSocket-соединения работают в отдельных потоках пула. EventBus использует Qt-сигналы с Qt::QueuedConnection — это автоматически маршрутизирует вызовы в нужный поток.

**— Почему выбрана именно Bybit, а не другая биржа?**
Bybit имеет подробную документацию WebSocket API и позволяет работать без аутентификации для публичных данных. Архитектура через IConnector позволит добавить другие биржи в будущем.

**— Что такое delta-обновления в стакане заявок?**
Биржа сначала присылает полный снимок стакана (snapshot), а затем только изменения (delta) — уровни, которые появились или исчезли. Это экономит трафик и ускоряет обновление.

**— Как именно вы отличаете спуфинг от обычной торговли?**
Когда объём на уровне цены падает, я сверяю величину падения с суммой реальных сделок по этой цене за тот же промежуток времени, взятых из ленты Time & Sales. Если падение объясняется исполненными сделками — это честная торговля. Если объём исчез без сделок — это отмена заявки, потенциальный спуфинг. Результат — не жёсткая метка, а доля необъяснённого падения, признак `fakeRatio`, который передаётся модели как ещё один входной признак.

**— Почему CatBoost, а не нейросеть, например LSTM?**
Данные табличные — один пример это один момент времени с фиксированным набором числовых признаков, а не последовательность. Для такой задачи градиентный бустинг на деревьях решений исторически показывает лучшее качество и требует значительно меньше данных для обучения, чем последовательные нейросети. CatBoost к тому же нативно обрабатывает категориальные признаки и имеет готовую C++-обёртку для интеграции прямо в терминал.

**— Что происходит с моделью, когда скользящее окно данных обновляется?**
Данные хранятся в структуре FIFO — новые добавляются, старые, вышедшие за пределы окна, автоматически удаляются и больше не участвуют в анализе. Модель при этом не дообучается инкрементально поверх себя же — это привело бы к тому, что устаревшие паттерны навсегда остаются зашитыми в деревьях, даже после того, как исходные данные удалились. Вместо этого модель периодически переобучается с нуля на текущем содержимом окна — это даёт настоящий эффект «забывания» устаревшего поведения рынка.

**— Как формируется целевая метка (target) для обучения?**
Для каждой строки признаков ищется точка в истории через заданный горизонт времени вперёд, и сравнивается цена в этот момент с текущей — рост или падение. Это упрощённая версия метода Triple Barrier: в перспективе планируется полноценная реализация с барьерами по take-profit и stop-loss через ATR, где метка ставится по тому барьеру, который сработал первым.

**— Тестировалась ли система под нагрузкой?**
Терминал тестировался на реальных данных Bybit в режиме реального времени. При одновременной работе графика, стакана и ленты сделок по паре BTCUSDT рендеринг остаётся стабильным на 60 FPS. Модуль сбора данных также проверен вживую — на реальном потоке стакана и сделок BTCUSDT, с корректной записью CSV с рассчитанными признаками.
